# Oasis Engine Gap Analysis & Wish List

## 1. Executive Summary
The Oasis Engine is a robust, event-driven gamification engine built on the Akka Actor model and Spring Boot. It supports core gamification elements (Points, Badges, Milestones, Ratings, Challenges) and features a scalable, distributed architecture. The system is well-structured with clear separation of concerns between the API (Service Layer) and the Execution Engine (Actor System).

Recent improvements have added real-time rule updates, eliminating the need for engine restarts. However, analysis reveals potential bottlenecks in rule execution scalability and Redis interaction patterns that should be addressed for high-volume production environments.

## 2. Architecture Overview
*   **Core Framework**: Akka (Java) for the execution engine, Spring Boot for management APIs.
*   **Persistence**: Redis (Redisson) for state management and leaderboards.
*   **Messaging**: RabbitMQ/Kafka for event ingestion (via `ExternalParty`).
*   **Execution Model**:
    *   `GameSupervisor`: Manages game lifecycles.
    *   `RuleSupervisor`: Routes events to executors.
    *   `RuleExecutor`: Executes rules sequentially for a given partition.
    *   `SignalSupervisor`: Handles rule outputs (Signals) and feedback loops.

## 3. Gap Analysis

### 3.1 Functionality
| Feature | Status | Notes |
| :--- | :--- | :--- |
| **Rule Types** | ✅ Excellent | Points, Badges, Milestones, Ratings, Challenges are fully supported. |
| **Meta-Rules** | ✅ Supported | Signals (Points, Badges) implement `EventCreatable`, allowing them to trigger subsequent rules. |
| **Real-time Updates** | ✅ Implemented | Rules can be added/removed/updated without restarts (recent fix). |
| **Leaderboards** | ✅ Supported | Redis Sorted Sets are used for efficient ranking. |
| **Multi-tenancy** | ✅ Supported | `GameSupervisor` isolates games by ID. |
| **Simulation** | ⚠️ Partial | `simulations` folder exists, but a dedicated "Dry Run" mode for testing rules on live data without side effects is missing. |

### 3.2 Performance
| Area | Status | Concern |
| :--- | :--- | :--- |
| **Rule Execution** | ⚠️ Warning | `RuleExecutor` iterates through *all* rules for a game sequentially (`while (allRulesForEvent.hasNext())`). This is O(N) per event. For games with thousands of rules, this will increase latency. |
| **Persistence** | ⚠️ Warning | Each rule execution that awards points/badges triggers a Redis write. There is no obvious batching or pipelining in `RuleExecutor`, potentially leading to high I/O overhead under load. |
| **Throughput** | ℹ️ Info | Single `RuleExecutor` actor per partition. Vertical scaling is limited by single-threaded actor processing. |

### 3.3 Reliability & Stability
| Area | Status | Notes |
| :--- | :--- | :--- |
| **Error Handling** | ✅ Good | `RuleExecutor` catches exceptions and NACKs messages to the broker. `SignalConsumer` uses Circuit Breakers. |
| **State Recovery** | ✅ Good | Relies on Event Sourcing principles. If the engine crashes, unacknowledged messages are redelivered by the broker. |
| **Poison Pills** | ❌ Missing | If a specific event causes a crash (e.g., parsing error), it might cause an infinite retry loop. A Dead Letter Queue (DLQ) strategy is needed. |

### 3.4 Code Quality
| Area | Status | Notes |
| :--- | :--- | :--- |
| **Testing** | ✅ Good | Unit and Integration tests exist. Recent tests added for `RuleChangeEvent`. |
| **Modularity** | ✅ Excellent | Clear separation between `core`, `engine`, `elements`, and `services`. |

## 4. Todo / Wish List

### High Priority (Performance & Stability)
1.  **Optimize Rule Execution (Rule Indexing)**:
    *   **Problem**: The current $O(N)$ iteration over all rules is inefficient.
    *   **Solution**: Maintain a `Map<EventType, List<Rule>>` in memory. When an event arrives, only fetch and execute the rules subscribed to that specific Event Type.
    *   *(Note: Distributed scaling is handled by the Message Broker via Partition Keys, so no Engine sharding logic is required).*
2.  **Redis Pipelining (Write Optimization)**:
    *   **Safe Batching**: This is a low-risk optimization. It purely batches the write operations (e.g., `INCRBY`) generated by a single event into one network packet.
    *   **Benefit**: Reduces network round-trips (RTT) significantly, making the "instant" feedback faster without risking data consistency.

### Medium Priority (Features)
4.  **Dry-Run / Simulation Mode**:
    *   Add an API to test rules against historical data or incoming events without committing changes to Redis.
5.  **Rule Dependency Graph**:
    *   **Visualization**: Gamification logic often involves chains (e.g., "Badge A" awards "100 Points").
    *   **Implementation**: Analyze rules implementing `EventCreatable`. Build a Directed Acyclic Graph (DAG) where Nodes are Rules and Edges are the Signals they produce. This allows admins to visualize the "Blast Radius" of a rule change (e.g., "If I change this Badge, it affects these Point calculations").

### Low Priority (Maintenance)
6.  **Enhanced Metrics**:
    *   Expose Akka metrics (mailbox size, processing time) to Prometheus/Grafana for better observability.
7.  **Documentation**:
    *   Generate architectural diagrams from the current code structure.
